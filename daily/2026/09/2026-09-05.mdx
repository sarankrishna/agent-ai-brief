## Three signals that should change your mental model

### Agents are becoming control-plane interfaces
Intuit reports eight months of using an agent over a deterministic disaster-recovery system, while AWS describes an agent-driven HyperPod control plane. The model selects among typed operations, and conventional APIs own validation, idempotency, authorization, retries, and audit.

**Why it matters:** The useful abstraction is a guarded control-plane contract, not an LLM with broad CLI access.

**Architectural consequence:** Put agent-facing tools in front of durable APIs with explicit state and completion criteria. Keep the agent out of the data path and make every state-changing action reviewable.

**Direct sources:** [Intuit EWOK Agent](https://aws.amazon.com/blogs/machine-learning/how-intuit-built-an-agentic-disaster-recovery-assistant-with-amazon-bedrock/), [HyperPod InstantStart](https://aws.amazon.com/blogs/machine-learning/run-agent-driven-amazon-sagemaker-hyperpod-operations-with-instantstart/)

### Memory needs retention engineering
AWS frames agent memory as a managed resource with distinct episodic, semantic, and procedural lifecycles, including TTL expiration, relevance decay, consolidation, pruning, and audit logging.

**Why it matters:** An agent can become less reliable and less compliant by remembering too much, not only by forgetting.

**Architectural consequence:** Define retention, freshness, provenance, deletion, and regression tests for memory before treating persistent memory as a feature.

**Direct source:** [AgentCore memory lifecycle policies](https://aws.amazon.com/blogs/machine-learning/designing-lifecycle-policies-for-agentcore-memory/)

### Capability-cost competition is moving to specialized inference paths
Microsoft launched MAI-Image-2.6 and a Flash variant for latency-sensitive, high-throughput workloads. Google also expanded Lyria 3.5 to the Gemini API. The pattern is capability-specific variants exposed through a common platform.

**Why it matters:** Routing, latency, modality, and unit economics become first-class application concerns.

**Architectural consequence:** Keep model selection behind a stable task interface and measure quality, latency, and cost on representative workloads.

**Direct sources:** [MAI-Image-2.6](https://microsoft.ai/news/pushing-the-quality-cost-frontier-with-mai-image-2-6/), [Lyria 3.5](https://blog.google/innovation-and-ai/products/gemini-app/better-tracks-lyria-gemini/)

## Architecture patterns emerging

### 1. Put agents above a durable control-plane contract
**Evidence:** Intuit places EWOK below the reasoning layer; HyperPod InstantStart routes UI, REST, and MCP through the same guarded APIs.
**Implication:** Expose typed operations with authorization, idempotency, persisted state, retries, and completion semantics. Do not give the model a raw administrative shell.
**Architect question:** Which invariants must be enforced in the API so every client receives the same safety properties?

### 2. Treat agent state as governed data
**Evidence:** AWS separates memory types and lifecycle policies; Intuit returns execution IDs and change records for operational state.
**Implication:** Model state needs ownership, retention, deletion, provenance, audit, and regression tests. Transcript length is not a memory architecture.
**Architect question:** Can every durable fact or operational transition be traced to its source, policy, and last validated use?

### 3. Route by workload objective, not one default model
**Evidence:** MAI-Image-2.6 has full and Flash variants; Lyria 3.5 targets a distinct media workload and API surface.
**Implication:** Define task-level SLOs and route among models based on quality, latency, cost, modality, and risk.
**Architect question:** What measurements will permit routing changes without hiding quality regressions?
